# OAS v0.19.0

One public release, built from one tag: `@oas-framework/oas@0.19.0`,
`@oas-framework/pi@0.19.0`, and **OAS Desktop 0.19.0** (attached to this GitHub
Release).

This release adds **distribution packages** — the install/update/review unit
above capabilities, with a v2 lock, exact restore, per-capability trust and
config profiles — makes the instance curriculum **exact and fail-closed**, and
makes instance homes **canonical**. Desktop CLI API v1 remains the
compatibility boundary; Desktop 0.19 accepts `desktopApi === 1` and semver
`>=0.18.0 <0.20.0`, so it pairs with both the 0.18.x and 0.19.x CLI lines.

## Upgrading from 0.18.x

**Your existing capabilities keep working.** v1 capability locks
(`lockfileVersion: 1`), their installed stores, and every `from: installed`
activation in your config behave exactly as they did in 0.18.x. Bare
`oas install` still restores them through the capability path and marks the
scope `LEGACY`; `oas doctor` warns that the lock is `lockfileVersion 1` and
points at `oas migrate`. Nothing is migrated automatically, and no config,
target or setting changes underneath you.

Four behaviours do change, deliberately:

- **Instance homes always land in the soul-owning repository's primary
  checkout.** Discovery still finds the agents root from wherever you invoke
  OAS, but when that root is inside a *linked git worktree*, storage maps to
  the equivalent path in the primary checkout. Homes survive the worktree and
  stay visible to the whole deployment. When placement cannot be established,
  the spawn fails closed with `E_NO_CANONICAL_ROOT` and creates nothing.
  Non-Git agents roots are unaffected.
- **A spawn fails when the composition declares resources that do not exist.**
  Previously an instance could start with a capability skill directory or
  injection silently absent while its instructions still referred to it; now it
  fails with `E_CAPABILITY_RESOURCE_MISSING`, naming each missing resource.
  Resources must resolve from the capability's locked/materialized content.
- **A capability's `spawn` hook may declare `required: true`.** Its failure now
  fails the spawn and rolls it back, instead of producing an instance whose
  capability never configured itself — an aweb identity that could not be
  minted leaves an agent believing it can be woken by mail. Only `spawn` hooks
  can be required; every other hook stays advisory. When rollback cannot
  finish, the home is **retained and quarantined** rather than deleted:
  `oas status` reports it as retained state, `oas retire <instance>` retries and
  must prove the outstanding cleanup ran, and `oas retire <instance> --force`
  is the escape hatch that removes it and prints whatever external state you now
  own.
- **pi sessions start with ambient skill and context discovery disabled** (see
  the curriculum section below).

**Official packages and the catalog are not part of this release.** The source
grammar reserves official catalog ids, but no catalog ships in 0.19.0 — an
install by catalog id fails closed with `the official package catalog cannot
resolve "<id>"`. Install packages from Git or local paths for now. The seeded
official catalog and the guided one-shot migration of existing deployments onto
official packages are planned for **0.19.1**; `oas migrate` in 0.19.0 maps a
scope's v1 capability locks into a v2 lock and keeps anything with no published
package as flagged legacy residue.

## Distribution packages

A **distribution package** is a directory with an `oas-package.json` that
declares what it ships. `capabilities` and `configs` are **independently
optional**, so all three shapes are valid: a package of capabilities with no
profile (`oas init --package` then reports `E_NO_PROFILES`), a **config-only**
package that ships reference profiles and exports no capability at all
(`oas list` shows `exports capabilities: (none)`, and the lock records
`capabilities: []`), or both together. A capability remains the
targeting/activation unit: every capability a package does export stays
independently addressable by ID with `from: installed`.

```bash
oas install git:github.com/org/repo@v1.0.0     # → the repo's oas-package/ (default)
oas install ../my-package                      # local path (that exact directory)
oas list                                       # installed packages, capabilities, scopes
oas update <package>                           # transactional re-resolve + diff + trust reset
oas remove <package>                           # refuses while config/dependents reference it
oas migrate [--dry-run]                        # map v1 capability locks to package locks
oas install                                    # bare: exact restore of this chain's locks
```

Every one of these supports `--json` (one stdout envelope, stable error codes)
and noninteractive operation, and the kernel-owned `oas-packages` skill —
composed into every instance — teaches the lifecycle.

### Where the package lives inside a repository

A Git repository **contains** a package rather than being one, so the source
spelling selects which directory:

| Source | Installed root |
| --- | --- |
| `git:github.com/org/repo@v1.0.0` | the repo's **`oas-package/`** (the default) |
| `git:github.com/org/repo@v1.0.0#dist/oas` | the repo's `dist/oas/` |
| `git:github.com/org/repo@v1.0.0#.` | the **repository root** — must be explicit |
| `/repo/custom-root` | that exact directory (local paths take no fragment) |

Only the selected subtree is installed and hashed, so repository docs, CI
configuration, owner souls and sibling packages stay outside the package's
installed bytes and integrity, and one repository may ship several packages at
different paths. The lock pins the selected root in its own `path` field, and
only an explicit `oas update <package>` may move it.

**A repository-root package needs `#.`.** Omitting the fragment selects
`oas-package/` — the convention every official example and scaffold uses — and
does not fall back to the root.

### Lock v2, restore, and trust

Installed package roots land in the owning scope's
`.agents/packages/installed/<package>/` (gitignored like the capability store)
and `oas-lock.json` becomes `lockfileVersion: 2`: a `packages` map with exact
source, commit, tree integrity, exported capability list, dependency closure,
and per-capability approvals. Schemas ship with the package
(`docs/oas-package.schema.json`, `docs/oas-lock.schema.json`); the contract is
`docs/design/package-engine-contract.md`.

Dependencies are pinned (tag/commit or local path — no semver solver); cycles
and two sources claiming one package identity at a scope are errors with
provenance. Acquisition **activates nothing**, and an unpinned Git source
resolves once and never advances on restore.

Trust binds to the capability inside the package at that package's exact
integrity: `oas trust <capability>` approves only that capability's
commands/hooks, and `oas trust <package> --all-capabilities` is the explicit
bulk path that prints the full executable surface first. Any integrity change,
including `oas update`, invalidates every approval. Skill/instruction/config-only
capabilities need lock integrity but no executable approval. A package may carry
a checked-in `package-lock.json` for JS runtime dependencies; OAS materializes it
with `npm ci --ignore-scripts` only — npm lifecycle scripts never run at
acquisition.

### Config profiles

A profile is a complete reference `oas-config.yaml` shipped by a package.
Adopting one is explicit and validated before anything is written:

```bash
oas init --package ../engineering-oas --config minimal
oas config diff        # report-only drift against the package's current profile
```

The adopted snapshot is an **ordinary scoped config** — not live inheritance.
`oas use`, `oas type`, `oas inject eject` and hand edits keep their meaning,
package updates never rewrite it, and a nested repository's config still wins per
the normal cascade. Nothing a package ships is mandatory.

### Workspace reconciliation

At a config scope that declares `team:`, bare `oas install` prints the chosen
boundary **before any network or host work**, then reconciles the whole
workspace: the boundary scope's locked graph, then each descendant scope
containing a config or lock, in deterministic order, pruning `.git`, generated
stores, dependency/vendor directories, agent instances and worktrees, and nested
team boundaries. Failures and missing requirements aggregate **by scope**. At a
non-team scope the current-chain behaviour is unchanged; `--recursive` requests
descendant reconciliation outside a team boundary. OAS never scans downward from
a laptop/home config by default.

### Host and runtime requirements — a separate consent gate

A capability's `requires` entry can declare structured, platform-aware install
methods, and a new kind of requirement: a **runtime package** (`runtime` +
`package`) satisfied by that runtime's own package manager — `npm:@scope/name`
for pi, `plugin@marketplace` for Claude Code. Runtime packages are raised only
for deployments that use the named runtime, verified in the runtime's package
list rather than on `PATH`, and **verified at spawn, never installed there**.

Installs stay consented and explicit: allowlisted managers only (`npm-global`,
`brew`), recipes as argv arrays and never shell snippets, no sudo, per-requirement
consent showing every step of a multi-step plan, `--accept-requirement <name>`
for automation, and `--no-requirements` for CI. A consented install that fails
exits nonzero; a declined one leaves an actionable `oas doctor` warning. Consent
to install a binary is separate from capability trust, in both directions.

## Exact OAS-managed curriculum

Every instance gets an exact `.agents/skills/` composed from the kernel, the
soul, and the selected capabilities, and `instance.json` now records what the
instance **actually** exposes under `composition.materialized.runtimePosture` —
the honest contract, not an aspiration. The two runtimes take deliberately
different ambient postures:

- **pi** launches with `--no-skills --skill <instance-home>/.agents/skills
  --no-context-files --no-prompt-templates` and an explicit
  `--append-system-prompt`: no user, project, ancestor or package skill
  catalogs, and no auto-injected `AGENTS.md`/`CLAUDE.md`. Your globally
  configured **pi extensions stay ambient on purpose**, and anything they
  contribute comes with them. Built-in tools and pi's interaction model are
  untouched.
- **Claude** runs provider-native: it reads the instance's `.claude/skills` and
  `CLAUDE.md` symlinks while **keeping your own Claude Code configuration** —
  user and project skills, plugins and settings all still apply, because they
  are useful and it is your choice to use them. Neither runtime gets a
  redirected config home.

Duplicate skill directory names remain an error unless config's
`skill-overrides` selects a source.

## Claude launch

- The prompt is passed after a `--` separator, so a capability launch hook
  contributing a greedy flag can no longer swallow the task text and drop the
  window to a fallback shell.
- A soul's `model` is translated to what the `claude` CLI accepts:
  `anthropic/<id>[:thinking]` becomes the bare `<id>`, aliases and bare
  `claude-*` ids pass through, other providers' entries are dropped, and nothing
  usable falls back to Claude's own default.
- `oas-claude-config` — the one-line local file naming the `claude` binary to
  launch (account selection on a personal machine) — is now gitignored by
  contract.

## Canonical instance homes and `OAS_INSTANCE_HOME`

Every instance is told its own home as **`OAS_INSTANCE_HOME`** (absolute), the
runtime-neutral name exported to every runtime; `PI_AGENT_HOME` /
`PI_AGENT_INSTANCE` remain compatibility aliases for the separately published pi
extension. Lifecycle hooks receive `OAS_INSTANCE_HOME` alongside the existing
`OAS_HOME`, which is kept because shipped capability hooks read it and is not
exported to runtime sessions. Neither is `OAS_HOME_DIR`, which is the package
store root.

Invocation directory, config/package scope (steerable with `--dir <path>`), and
the instance's `work/` view stay independent — only *storage* is canonicalized.

Generated instructions now open with the home/work boundary: the instance home
holds the brain, task, provenance and episodic state and is where OAS and
capability commands run; `work/` is where repository work happens; the home's
`soul` link is read-only, because writes through it bypass the branch and review
path.

**Deployment prerequisite:** the agents root, `local-agents/` and the instance
homes under them must be operator-owned and not writable by untrusted users or
processes. OAS validates resolved destinations and re-checks the home immediately
before creating anything in it, but a local attacker who already has write access
there also controls souls, instructions and hook declarations — this is a
filesystem-ownership prerequisite, not something the kernel can close from inside.

## Desktop

- **Terminal splits follow VS Code editor-group semantics**, with a dedicated
  full-width tab-group row sharing the panes' width track, clickable
  split/sidebar controls, and split-aligned tab strips.
- **Quick Open** hands off to Spawn through a consumed-once preselect: a
  CLI-ready spawnable soul opens the modal, anything else reveals and focuses its
  card.
- The spawn modal's **model dropdown** is filled from a runtime-scoped catalog
  served behind the backend's Origin guard, with a coalesced probe and a
  per-request fill token.
- Spawn handoff waits for terminal readiness, closes the modal, and opens the
  terminal quietly; quiet opens contain **all** rejections, and a pane
  re-render no longer steals focus from the group you just created.
- The accepted CLI band is now `>=0.18.0 <0.20.0` with Desktop API v1, so this
  Desktop pairs with the 0.19.0 CLI it ships beside as well as with any 0.18.x
  install. Spawn-time agent relations still require an `oas` CLI `>= 0.18.6`;
  the relation controls stay visible and fail closed below it.

| macOS x64 (Intel) | DMG + ZIP |

The macOS artifacts are ad-hoc signed — not Developer ID signed and not
notarized. First launch may still require right-click → **Open** (or **Open
Anyway** in System Settings → Privacy & Security).

Verify downloads with `SHA256SUMS.txt`; GitHub build-provenance attestations are
published for all assets.

## Install / update

```bash
npm install -g @oas-framework/oas@0.19.0
```

The pi bridge `@oas-framework/pi` publishes in lockstep. Desktop downloads are
the assets on this release; the full install/support guide is
[docs/desktop.md](https://github.com/OAS-Framework/oas/blob/main/docs/desktop.md).
